05 PAYMENTS

Four eyes on every
withdrawal above your threshold.

Withdrawals move through explicit states. Limits by role and player category decide who may approve, and a second person approves above the threshold.

  • Handling-time target

    Each request shows how long it has waited and is flagged past your target; a report measures time to payment.

  • Approval tiers

    Each role approves up to its limit; above the category threshold, a different person gives the second approval.

  • Cashier limits

    Minimum and maximum deposits and withdrawals, and withdrawal counts per period, by player category.

  • Unmatched payments

    Incoming payments that match no player are linked to an account or returned; one person requests, another approves.

  • Adjustment batches

    Credits and debits for up to 200 accounts from a CSV, previewed line by line and approved by another person.

  • Ledger search and export

    Search the ledger by ID or payment-provider reference and export up to 5,000 rows as CSV.

06 COMPLIANCE & CONTROL

Controls you can

  • Audit trail

  • Responsible gaming

    Self-exclusions, pauses and limits, including requests recorded by an agent.

  • KYC queue

  • Data-subject requests

    Privacy requests tracked against their deadlines.

  • Policies and terms

    Published versions, with each player's acceptance on record.

  • Jurisdiction parameters

    Market settings, including the display time zone, published by authorized staff.

  • Permissions by role

    Every screen and action tied to a permission, granted through five staff roles.

08 SECURITY & INTEGRATION

Built API-first.
Secured on the server.

Staff work in the browser; only the server can read their session and tokens, and authorization is checked on the server and in the API.

  • API-first

    Every screen reads and writes through the Sentinel API, the same API your platform integrates with.

  • Sealed session cookie

    An encrypted, HttpOnly cookie that only the back-office server can open, so access tokens are never readable in the browser.

  • Sign-in through an identity provider

    Staff sign in through OpenID Connect; the back-office never sees a password.

  • Operator separation

    Each operator's data is kept apart, and the API authorizes every request.

  • Masked player data

    Personal data is masked by default; revealing it needs a permission.
